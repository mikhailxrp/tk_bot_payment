# Phase 10 — Панель: дашборд и активность в группе

## Статус

⏳ Ожидает (стартует сразу после Фазы 8, не дожидаясь Фазы 9) | Ветка: `phase-10`

## Цель

После этой фазы `/dashboard` показывает: выручку (день/месяц, с разбивкой по продуктам), MRR,
счётчики статусов подписчиков, новые подписки за период, конверсию /start→оплата, win-back rate,
график платежей — и новый блок активности в закрытой группе: DAU/WAU, график сообщений по дням,
топ активных участников, долю «тихих» ACTIVE-подписчиков (0 сообщений за 7 дней — сигнал риска
оттока). Активность собирается ботом в фоне с этой же фазы.

## Контекст

Опирается на Фазу 8 (✅ ожидается): рабочий `apps/admin` с auth и layout. **Не зависит от Фазы
9** — дашборд только читает БД через Prisma, internal API бота (появляется в Фазе 9 для
ban/unban-действий из панели) здесь не нужен; отклонение от исходного порядка зафиксировано в
`_status.md` (2026-09-12).

Данных для активности в группе сейчас нет вообще — ни в схеме, ни в коде бота. Бот уже состоит
администратором закрытой группы (нужно для `banChatMember`/`unbanChatMember`, см. CLAUDE.md
п.6) — по правилам Bot API это значит, что боту доставляются **все** сообщения группы независимо
от privacy mode, дополнительных прав включать не нужно.

Решение по хранению активности (принято при постановке задачи): не логировать сообщения
целиком (лишняя нагрузка на БД, не нужно для метрик), а хранить **дневные агрегаты**
`(userId, date, messageCount)` — отдельная таблица `GroupActivity`, день — календарная дата по
Europe/Moscow (проект уже использует эту таймзону для cron, см. `util/moscowDate.ts`). Обычные
данные для остальных метрик берутся из уже существующих моделей: `Payment` (выручка/MRR/график),
`User` (статусы/новые подписки — `createdAt`/`status`), win-back — доля `User` с историческими
переходами `MUTED→ACTIVE` (по факту `Payment.PAID` после того, как `status` был `MUTED`).

Разделы PRD: 5.1 (таблица разделов, обновлена), 6 (модель данных — добавлена `GroupActivity`).
CLAUDE.md рулит по BigInt (п.8, JSON-сериализация в панели) и настройкам без кэша (п.12) —
здесь не затрагиваются напрямую, но применимы к любым новым server actions/queries.

## Таски

### Task 10.1 — DB: миграция `GroupActivity`

- **Статус:** ⏳ Ожидает
- **Workspace:** db
- **Цель:** новая модель для дневных агрегатов активности.
- **Файлы:** `packages/db/prisma/schema.prisma` (модель `GroupActivity { userId, date,
  messageCount }`, композитный `@@id([userId, date])`, обратная связь на `User`), миграция
  `npx prisma migrate dev --name add_group_activity -w packages/db`.
- **Out of scope:** запись данных (Task 10.2), чтение для дашборда (Task 10.3).
- **DoD:**
  - [ ] миграция применяется на реальной БД без ошибок, `prisma generate` подхватывает новую
        модель в обоих приложениях
  - [ ] `@@id([userId, date])` гарантирует один ряд на пользователя в день (upsert, не insert)

### Task 10.2 — Bot: трекинг активности в закрытой группе

- **Статус:** ⏳ Ожидает
- **Workspace:** bot
- **Цель:** хендлер сообщений группы инкрементирует дневной агрегат.
- **Файлы:** `apps/bot/src/bot/handlers/groupActivity.ts` (новый: `bot.on('message')`,
  фильтр `ctx.chat.id === config.GROUP_ID`, игнорировать `ctx.from.is_bot`, upsert
  `GroupActivity` с `messageCount: increment(1)`), `apps/bot/src/bot/bot.ts` (регистрация
  хендлера на `subscriptionBot`, вне `subscriptionPrivate` — это групповой чат),
  `apps/bot/src/util/moscowDate.ts` (переиспользовать/расширить для «начало текущего
  московского дня» на момент сообщения, а не только границ текущего дня).
- **Out of scope:** трекинг общей группы (вне скоупа PRD — метрики только по закрытой),
  чтение агрегатов (Task 10.3).
- **DoD:**
  - [ ] сообщение от реального пользователя в закрытой группе увеличивает
        `GroupActivity.messageCount` за текущий московский день на 1
  - [ ] сообщения от ботов (`ctx.from.is_bot`) не учитываются
  - [ ] сообщения вне `GROUP_ID` (например, в общей группе или личке) не создают записей
  - [ ] сбой записи (БД недоступна) логируется и не роняет обработку остальных апдейтов бота

### Task 10.3 — Admin: агрегационные запросы для дашборда

- **Статус:** ⏳ Ожидает
- **Workspace:** admin
- **Цель:** серверные функции чтения метрик (Prisma `groupBy`/`aggregate`/raw SQL, без кэша).
- **Файлы:** `apps/admin/src/lib/dashboard/revenue.ts` (выручка день/месяц по продуктам, MRR),
  `apps/admin/src/lib/dashboard/subscribers.ts` (счётчики статусов, новые подписки, конверсия
  /start→оплата, win-back rate), `apps/admin/src/lib/dashboard/activity.ts` (DAU/WAU, ряд для
  графика сообщений, топ-10 активных, % «тихих» ACTIVE).
- **Out of scope:** UI/графики (Task 10.4).
- **DoD:**
  - [ ] выручка/MRR за произвольный период совпадают с ручным `SELECT SUM(amount) ... WHERE
        status='PAID'`
  - [ ] конверсия /start→оплата = доля `User`, у которых есть хотя бы один `Payment(PAID)`,
        среди `User`, созданных за период
  - [ ] win-back rate = доля пользователей с `mutedAt IS NOT NULL`, у кого после этого появился
        `Payment.PAID`, среди всех когда-либо `MUTED` за период
  - [ ] DAU = число уникальных `userId` в `GroupActivity` за день; WAU — за 7 дней; сходится с
        ручным `COUNT(DISTINCT userId)`
  - [ ] «тихие» = `User.status = ACTIVE` без ни одной строки `GroupActivity` за последние 7 дней
