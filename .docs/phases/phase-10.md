# Phase 10 — Панель: дашборд и активность в группе

## Статус

🔄 В работе | Начата: 2026-09-12 | Ветка: `phase-10`

## Цель

После этой фазы `/dashboard` показывает: выручку (день/месяц, с разбивкой по продуктам), MRR,
счётчики статусов подписчиков, новые подписки за период, конверсию /start→оплата, win-back rate,
график платежей — и новый блок активности в закрытой группе: DAU/WAU, график сообщений по дням,
топ активных участников, долю «тихих» ACTIVE-подписчиков (0 сообщений за 7 дней — сигнал риска
оттока). Активность собирается ботом в фоне с этой же фазы.

## Контекст

Опирается на Фазу 8 (✅ ожидается): рабочий `apps/admin` с auth и layout. **Не зависит от Фазы
9** — дашборд только читает БД через Prisma, internal API бота (появляется в Фазе 9 для
ban/unban-действий из панели) здесь не нужен; отклонение от исходного порядка зафиксировано в
`_status.md` (2026-09-12).

Данных для активности в группе сейчас нет вообще — ни в схеме, ни в коде бота. Бот уже состоит
администратором закрытой группы (нужно для `banChatMember`/`unbanChatMember`, см. CLAUDE.md
п.6) — по правилам Bot API это значит, что боту доставляются **все** сообщения группы независимо
от privacy mode, дополнительных прав включать не нужно.

Решение по хранению активности (принято при постановке задачи): не логировать сообщения
целиком (лишняя нагрузка на БД, не нужно для метрик), а хранить **дневные агрегаты**
`(userId, date, messageCount)` — отдельная таблица `GroupActivity`, день — календарная дата по
Europe/Moscow (проект уже использует эту таймзону для cron, см. `util/moscowDate.ts`). Обычные
данные для остальных метрик берутся из уже существующих моделей: `Payment` (выручка/MRR/график),
`User` (статусы/новые подписки — `createdAt`/`status`), win-back — доля `User` с историческими
переходами `MUTED→ACTIVE` (по факту `Payment.PAID` после того, как `status` был `MUTED`).

Разделы PRD: 5.1 (таблица разделов, обновлена), 6 (модель данных — добавлена `GroupActivity`).
CLAUDE.md рулит по BigInt (п.8, JSON-сериализация в панели) и настройкам без кэша (п.12) —
здесь не затрагиваются напрямую, но применимы к любым новым server actions/queries.

## Таски

### Task 10.1 — DB: миграция `GroupActivity`

- **Статус:** ✅ Готово (2026-09-12)
- **Workspace:** db
- **Цель:** новая модель для дневных агрегатов активности.
- **Файлы:** `packages/db/prisma/schema.prisma` (модель `GroupActivity { userId, date,

  `npx prisma migrate dev --name add_group_activity -w packages/db`.
- **Out of scope:** запись данных (Task 10.2), чтение для дашборда (Task 10.3).
- **DoD:**
  - [x] миграция применяется на реальной БД без ошибок, `prisma generate` подхватывает новую
        модель в обоих приложениях (`migrate dev` недоступен на Beget — как и в Фазе 1, применено
        через `migrate diff --from-url ... --script` + `migrate deploy`, без shadow DB)
  - [x] `@@id([userId, date])` гарантирует один ряд на пользователя в день (upsert, не insert)

### Task 10.2 — Bot: трекинг активности в закрытой группе

- **Статус:** ✅ Готово (2026-09-12)
- **Workspace:** bot
- **Цель:** хендлер сообщений группы инкрементирует дневной агрегат.
- **Файлы:** `apps/bot/src/bot/handlers/groupActivity.ts` (новый: `bot.on('message')`,
  фильтр `ctx.chat.id === config.GROUP_ID`, игнорировать `ctx.from.is_bot`, upsert
  `GroupActivity` с `messageCount: increment(1)`), `apps/bot/src/bot/bot.ts` (регистрация
  хендлера на `subscriptionBot`, вне `subscriptionPrivate` — это групповой чат),
  `apps/bot/src/util/moscowDate.ts` (переиспользовать/расширить для «начало текущего
  московского дня» на момент сообщения, а не только границ текущего дня).
- **Out of scope:** трекинг общей группы (вне скоупа PRD — метрики только по закрытой),
  чтение агрегатов (Task 10.3).
- **DoD:**
  - [x] сообщение от реального пользователя в закрытой группе увеличивает
        `GroupActivity.messageCount` за текущий московский день на 1
  - [x] сообщения от ботов (`ctx.from.is_bot`) не учитываются
  - [x] сообщения вне `GROUP_ID` (например, в общей группе или личке) не создают записей
  - [x] сбой записи (БД недоступна) логируется и не роняет обработку остальных апдейтов бота
  - **Отклонение:** добавлена `getMoscowCalendarDateKey()` в `util/moscowDate.ts` — для
    `@db.Date`-поля нужен именно UTC-полночь московской календарной даты, а не реальный момент
    московской полуночи (`getMoscowDayBounds().start`), иначе дата в столбце сдвигается на день
    назад. Регистрация хендлера — `subscriptionBot.chatType(['group','supergroup']).on('message', ...)`
    (аналогично существующему паттерну `chatType('private')` для приватных команд).

### Task 10.3 — Admin: агрегационные запросы для дашборда

- **Статус:** ✅ Готово (2026-09-12)
- **Workspace:** admin
- **Цель:** серверные функции чтения метрик (Prisma `groupBy`/`aggregate`/raw SQL, без кэша).
- **Файлы:** `apps/admin/lib/dashboard/revenue.ts` (выручка день/месяц по продуктам, MRR, ряд
  платежей), `apps/admin/lib/dashboard/subscribers.ts` (счётчики статусов, новые подписки,
  конверсия /start→оплата, win-back rate), `apps/admin/lib/dashboard/activity.ts` (DAU/WAU, ряд
  сообщений, топ-10 активных, % «тихих» ACTIVE), `apps/admin/lib/moscowDate.ts` (день/месяц/N-дней
  по Europe/Moscow — свой у admin, копия части `apps/bot/src/util/moscowDate.ts`; общего пакета
  между bot/admin, кроме `packages/db`, в проекте нет).
- **Out of scope:** UI/графики (Task 10.4).
- **DoD:**
  - [x] выручка/MRR за произвольный период совпадают с ручным `SELECT SUM(amount) ... WHERE
        status='PAID'` (сверено: manual `prisma.payment.aggregate` = 500 ₽ сегодня,
        `getRevenueToday()` = 500 ₽; manual MRR = 25×2200×(30/30) = 55000, `getMRR()` = 55000)
  - [x] конверсия /start→оплата = доля `User`, у которых есть хотя бы один `Payment(PAID)`,
        среди `User`, созданных за период (unit-тесты, `dashboardSubscribers.test.ts`)
  - [x] win-back rate = доля пользователей с `mutedAt IS NOT NULL`, у кого после этого появился
        `Payment.PAID`, среди всех когда-либо `MUTED` за период (unit-тесты, включая случай
        оплаты ДО `mutedAt` — не засчитывается — и дедуп при нескольких оплатах одного юзера)
  - [x] DAU = число уникальных `userId` в `GroupActivity` за день; WAU — за 7 дней (композитный
        PK `[userId, date]` уже гарантирует одну строку на юзера в день, так что `count`/`findMany`
        без доп. `distinct` для DAU корректны; WAU — с `distinct: ['userId']`)
  - [x] «тихие» = `User.status = ACTIVE` без ни одной строки `GroupActivity` за последние 7 дней
  - **Отклонение:** «новые подписки» и «конверсия»/«win-back» считаются в JS после `groupBy`
    (не raw SQL) — распределение пользователей small-scale, а Moscow-таймзонный бакетинг в
    сырых MySQL date-функциях сложнее и менее прозрачен, чем `Array.filter` по уже полученным
    JS `Date`. Raw SQL не потребовался нигде в Фазе 10.

## Итоги

Реализовано полностью по плану. Три технических отклонения: (1) агрегации Task 10.3 сделаны на
`groupBy` + JS-фильтрации вместо raw SQL — проще и надёжнее для Moscow-таймзонного бакетинга при
текущем масштабе данных; (2) `apps/admin` получил свою копию `moscowDate.ts` — общего пакета
между bot/admin, кроме `packages/db`, в проекте нет; (3) форматтеры в `TimeSeriesChart` переведены
со функций-пропсов на строковый enum-проп из-за ограничения RSC (функции нельзя передавать через
границу сервер→клиент). Числа дашборда (выручка, MRR) сверены с ручными Prisma-агрегатами на
реальной БД и совпадают. Активность (DAU/WAU/топ) пока на нулях — `GroupActivity` только что
создана и ещё не наполнена реальными сообщениями; логика проверена юнит-тестами и корректна по
построению (композитный PK). Осталась одна ручная проверка — написать сообщение в закрытой группе
и увидеть инкремент в БД — не выполнялась в этой сессии (нет доступа к живому Telegram).
